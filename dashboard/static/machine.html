Your Moodle work

Two Moodle sites and one shared toolbox, all in Docker. They restart on their own after a reboot (docker's unless-stopped), so you never start them by hand unless you stopped them yourself.

01Moodle 5.2, the dev site8052https 8452db 5452keep

This is where your plugins run. Two containers: moodle52-app-1 (Apache + PHP 8.4, up 9 days) and moodle52-db-1 (Postgres 16). The code is a folder on disk, ~/moodle-envs/5.2/www, mounted into the container, so editing a file on the laptop is editing it in the site. Release 5.2.3+, 17 fixture charts, the assistant client stays openai.

From the wifi you open port 8052 plainly; from the phone you open the https 8452 address, which is Tailscale terminating TLS and handing the request to 8052 on the loopback. Port 5452 is the database, reachable from the tailnet only, for a desktop SQL client.

needsdocker; the moodle-shared network must exist (the app joins it to reach MailHog and Selenium) if it stopsyour dev site is gone; PHPUnit and Behat have nothing to run in; the cron timer fails every minute stop / startdocker compose -f ~/moodle-envs/5.2/docker-compose.yml stop · … up -d

02MailHog, the mail catchersmtp 1025web 8025stoppable

Every email either Moodle site tries to send lands here instead of leaving the machine: password resets, forum digests, the test mails of a plugin. Open 8025 and read them. Nothing is ever really sent, which is exactly what you want on a dev box. Part of the moodle-shared stack with the proxy and Selenium.

needsdocker if it stopsMoodle's mail goes nowhere and its cron logs SMTP errors; the sites keep working stop / startdocker compose -f ~/moodle-envs/shared/docker-compose.yml stop mailhog · … up -d mailhog

03Selenium, the browser Behat drives444459007900stoppable

A headless Chrome 96 in a container, the one Moodle's Behat suite steers when you run acceptance tests. Port 4444 is the grid it listens on; a Behat run connects there and the browser lives inside the container's virtual screen.

Why the dashboard shows the noVNC viewer as down. Ports 5900 (VNC) and 7900 (noVNC, a browser-based VNC viewer) are published in the compose file, so docker accepts a connection on both. But inside this image nothing listens there: the process list is Xvfb, the Selenium grid and supervisord, no VNC server at all, and the only open port in the container is 4444. So a connection is accepted by docker's proxy and closed at once, and the panel reads that as down. It is accurate and harmless. Watching a Behat run live would need an image that ships a VNC server; the two port lines could just as well be removed.

needsdocker; 2 GB of shared memory and privileged for Chrome if it stopsBehat runs fail to start; PHPUnit and the sites do not care stop / startdocker compose -f ~/moodle-envs/shared/docker-compose.yml stop selenium · … up -d selenium

05Moodle cron, every minutemoodle52-cron.timerkeep

Moodle needs a cron heartbeat: scheduled tasks, adhoc tasks, mail sending, cache cleanup all wait for it. The timer runs admin/cli/cron.php inside its app container once a minute. Without it a site looks fine but adhoc tasks queue forever and nothing you enqueue in a plugin ever runs, which is a confusing way to lose an afternoon.

06moodle-keeper, the 04:30 backupagent@moodle-keeper.timerkeep

Every night it brings both envs up, waits for HTTP, dumps each database to ~/agents/backups/moodle/<env>/YYYY-MM-DD.sql.gz, restores the dump into a scratch database to prove it is real, prunes dangling docker images and rotates the logs. Last run this morning: 5.2 dumped at 1.8 MB and demo at 4.4 MB, both restored, 37 seconds. It is a bash script; Claude only wakes if the script fails.

These dumps are the only backup of your databases. There is no off-machine backup (the restic ticket was skipped by your decision). If the disk dies, the dumps die with it.

The Eye

The voice assistant: the green eye on the TV, the page on your phone, the ear that hears you and the mouth that answers. It is one node process plus a few helpers; the code lives in ~/the-dark-eye, separate from the fleet.

08dark-eye, the bodydark-eye.servicebridge 8642page 8644keep

One node process (body/src/main.js, up since this morning) that does three jobs. It draws the eye on the TV through a Rust renderer on the GPU. It runs the voice worker: speech to text when you talk, Kokoro text to speech when it answers. And it serves two small web things on the loopback only: the bridge on 8642, the local API every eye command talks to, and the page on 8644, which Tailscale publishes as https 8644 so your phone can tap, talk and hear replies.

Everything that "speaks" on this machine goes through it: agents announcing results, links landing on your page, the orbiters around the eye that light up for each running agent. Agents are told never to restart it, because a restart cuts you off mid-sentence.

The agent fleet

Agents that wake on a systemd user timer, do one bounded job, write a 5-line REPORT.md in their own folder under ~/agents/, and go back to sleep. Most of the work is bash; Claude is only called when bash cannot decide. Kill switch for all of them: agents-stop; back on: agents-start.

14sentinel-check, every 15 minutessentinel-check.timerkeep

The machine's immune system, and it is only a bash script. Every 15 minutes it reads pc status, and for a short list of known faults it applies the known fix: docker down, ydotoold down, Tailscale down, a Moodle stack down, the orchestrator session gone. It also kills runaway processes. Only if a fix fails does it call the sentinel agent (Claude) with the incident, and only if that fails do you get a push. Last run at 13:35 today, all clear. This is why things you never touch keep coming back after a hiccup.

needspc status, sudo for the restarts if it stopsnothing repairs itself any more; a docker or Tailscale wobble stays broken until you notice stop / startsystemctl --user stop sentinel-check.timer · … start … · the Claude fallback agent@sentinel.timer is disabled on purpose

Delete tomorrow, or it quietly breaks

The short answer to "could I switch this off".

delete tomorrow, lose nothing

  1. Portfolio preview on 8071 and its firewall rule: a hand-started server older than your repo's build.
  2. claude-orchestrator.service: disabled unit for a tmux session you do not use.
  3. mpris-proxy.service: enabled, dead, the earbud sidecar owns those keys.
  4. Selenium ports 5900 and 7900 in the shared compose file: mapped to nothing inside the image.
  5. hello agent folder: the runner template, disabled.

switch off, nothing visible today

  1. toolsmith: no more proposals.
  2. pcbench-weekly: the toolbox stops being measured.
  3. sentinel-digest: no 08:00 push.
  4. Selenium and MailHog while you are not testing: Behat and mail catching pause; up -d brings them back in seconds.
  5. netdata: the dashboard loses its sparklines.

would quietly break

  1. Moodle cron timers: sites look fine, but tasks and mails queue forever.
  2. moodle-keeper: backups stop aging forward; you learn it the day you need one.
  3. sentinel-check: nothing repairs itself; a wobble stays broken.
  4. ydotoold: agents can still see the screen but cannot touch it.
  5. etckeeper: config changes under /etc stop being recorded.

would break loudly

  1. tailscaled: phone loses everything, remote SSH included.
  2. docker: both Moodle sites, MailHog, Selenium.
  3. dark-eye: no eye, no voice, no phone page.
  4. agents-dashboard: this panel.
  5. ufw: nothing breaks, everything on your wifi opens up.
