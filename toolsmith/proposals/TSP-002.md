# TSP-002 — `--apply` invalidates the cache keys it changed (`pc status` stale profile, C02)

## Problem
`pc_apply` writes the ledger but never drops the `cached` entries for the target it changed, so `pc status` serves a 60 s stale `power_profile` after any `pc power profile --apply`, GNOME-menu change or bench teardown. Agents that read `pc status` first correctly do nothing on a lie.

## Evidence
- `bin/pclib.sh:195-221` — `pc_apply` has no cache write or delete.
- `bin/pc-status:288` — `cached power_profile 60 _profile`; `bin/pc-power:88` — `cached ppd 60`.
- `20260907-185621-ab/C02/new/3` — "power profile is performance, not balanced": read a stale `balanced`, concluded no-op (BASELINE-PCBENCH.md:118).
- `bench/tasks/C02/teardown.sh:8-9` — task-side workaround deletes the two keys by hand; the tool should.
- C02 is 1/3 new arm while C01/C03/C04/C05 are 3/3 (BASELINE-PCBENCH.md:129).

## Survey
- exists: power-profiles-daemon emits `ActiveProfileChanged` on D-Bus, https://freedesktop-team.pages.debian.net/power-profiles-daemon/gdbus-org.freedesktop.UPower.PowerProfiles.html (read 2026-09-07) — rejected: needs a resident `gdbus monitor`; `pc` has no daemon.
- chosen: (1) `pc_apply` deletes `$CACHE/<key>` for every key in a per-verb `PC_CACHE_KEYS` (pc-power sets `ppd power_profile`), after the mutation; (2) `pc status` reads `power_profile` live when the entry is older than the newest ledger line for `powerprofiles`.
- why: no daemon, one function, closes the class (docker/units/audio keys get the same hook for free).

## Proposed change
`bin/pclib.sh`: `pc_apply` → `rm -f` each key in `${PC_CACHE_KEYS:-}`. `bin/pc-power`, `pc-audio`, `pc-units`, `pc-docker`: export their keys. `bin/tests/pclib.test.sh`: a case that poisons `$CACHE/ppd` under a temp `XDG_RUNTIME_DIR` with stub `powerprofilesctl` and asserts the key is gone after `--apply`. Then `bench/tasks/C02/teardown.sh` lines 7-9 become redundant (leave until measured).

## Success check
- metric: C02 pass, new arm, n=3
- before: 1/3
- target: 3/3 on two consecutive weekly runs
- measured by: `pcbench report bench/runs/<sun> --task C02`
