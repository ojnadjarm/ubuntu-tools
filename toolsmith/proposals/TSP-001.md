# TSP-001 — `sudo` guard: close the secure_path hole in `bin/guards`

## Problem
The FLEET §5 refusal guards only work through PATH; `sudo` resets PATH via `secure_path`, so `sudo shutdown -r`, `sudo reboot`, `sudo systemctl stop tailscaled` reach the real binary unguarded.

## Evidence
- `bin/fleetlib.sh:17` — guards are only `$HARNESS_HOME/bin/guards` prepended to PATH.
- `bin/guards/` — contains `git halt poweroff reboot shutdown tailscale`; no `sudo`.
- `/etc/sudoers` — `Defaults secure_path="/usr/local/sbin:…:/snap/bin"` (read with `sudo -n grep`), guards dir not in it.
- `bin/maintenance-run:25` — the fleet's own reboot is `sudo shutdown -r +N`, i.e. it depends on the hole.
- `log/guards.jsonl` — 0 rows in 4 days while S-tier ran: no guard has ever fired on a sudo path.

## Survey
- exists: sudoers `Cmnd_Alias`/`!` rules (forbidden here: FLEET §5.3 bans sudoers edits); `agent-callable` deny-by-default PreToolUse wrapper for Claude Code, https://github.com/Evaneos/agent-callable (read 2026-09-07) — rejected: agent-CLI specific, would not cover `agent-exec` under another harness; sudo 1.9.16 `secure_path` default rationale, https://www.sudo.ws/posts/2024/09/why-sudo-1.9.16-enables-secure-path-by-default/ (read 2026-09-07) — confirms PATH shims can never be reached through sudo.
- chosen: a `bin/guards/sudo` wrapper that strips leading `-n/-E/-u X/-i`, applies the same `case` as the existing guards to the first non-option word (and to `systemctl stop|disable|mask <fleet unit>`), then execs the real `sudo`. `maintenance-run` keeps working because it runs inside the T23 window, which the reboot guard already honours.
- why: same file, same log, same three-part refusal; no sudoers change; no resident process.

## Proposed change
Add `bin/guards/sudo` (symlink to `_guard`, new `sudo)` case that re-dispatches on the wrapped command). Extend `bin/tests/guards.test.sh` with sudo cases against stub binaries in the temp dir (never the real ones). Note the hole and the fix in `KB/quirks.md`.
