## Defects

**D10 — HIGH — T28a — `pc see <SEL>` crashes with an unhandled `AttributeError` whenever any window
has a null title or null `wm_class`; a tooltip or an open menu is enough.**
- Repro (deterministic):
  ```
  pc open org.gnome.Calculator; pc wait-for --focus Calculator
  pc click $(pc tree gnome-calculator --find "Basic")   # opens a popover -> a title-less window
  pc see gnome-calculator     # traceback, exit 1
  pc see Calculator           # traceback, exit 1
  ```
  ```
  File "~/agents/bin/a11y_tree.py", line 275, in pick_window
    m = [w for w in wins if s in w.get("title", "").lower() or s in w.get("wm_class", "").lower()]
  AttributeError: 'NoneType' object has no attribute 'lower'
  ```
  `w.get("title", "")` returns the key's value `None`, not the default, because window-calls sends
  `"title": null` for popups/tooltips.
- Impact: the ticket's own `pc see [SEL]` form is unusable at exactly the moments an agent needs it —
  a menu or tooltip is open. It also fails loudly with a Python traceback rather than a `pc`-style
  message. `pc see` with no SEL is unaffected (exit 0).
- Fix: `(w.get("title") or "").lower()` and the same for `wm_class` in `pick_window()`
  (`a11y_tree.py:275`); the same pattern should be audited elsewhere in the file.

**D11 — HIGH — T28b — Chrome's a11y coordinates are missing the window origin, so every coordinate
`pc see` reports for web content is wrong by the frame offset and `pc a11y-click` on a page element
silently exits 0 and does nothing.**
- Repro:
  ```
  pc open https://example.com; pc wait-for --window "Example Domain" --timeout 15
  pc see | grep link          # link "Learn more" (259,293 83x20)   -> centre 300,303
  pc a11y-click "Learn more" --app "Google Chrome"   # exit 0, page does not navigate
  pc click 300 303                                   # nothing happens
  pc find "Learn more"                               # 368 334   <- the real position
  pc click 368 334                                   # navigates to iana.org ("Example Domains")
  ```
  Delta = `(+68, +31)`, and the Chrome window is at `+67+32`. The heading agrees: a11y y-centre 228
  vs OCR 260, again +32. A screenshot with the pointer at `368,334` shows Chrome's status bar
  reading `https://iana.org/domains/example`, i.e. the OCR position is the true one.
- Diagnosis: Chrome reports **window-relative** extents where `a11y_tree.py` treats them as already
  screen-absolute, so the GTK4 origin correction that works for GTK apps is skipped for Chrome.
- Impact: this is the headline of T28b ("the owner's Chrome shows up in `pc see` like any GTK app").
  Reading the tree works; *acting* on it does not, and it fails silently (exit 0), which is the worst
  failure mode — an agent will believe it clicked. The whole preference order collapses to OCR for
  any web page. Also blocks T14/Chrome work that relies on `pc see`.
- Fix: apply the same `frame origin + WINDOW extents` path to Chrome frames (detect it the way GTK4
  is detected — a frame whose SCREEN extents do not match `GetFrameRect`), and make `pc a11y-click`
  exit non-zero when neither a coordinate click nor `do_action(0)` produced any change (or at least
  when the node has no usable coordinates).

**D12 — MEDIUM — T28a — `pc see` / `pc tree` never read the AT-SPI `Text` interface, so every text
field and document body prints as `text ""`. The skill's and README's claim that `ui:` "reads
document text exactly where OCR misses lines (QA D4)" is false, and D4 is therefore still open.**
- Repro: two lines typed in gnome-text-editor (`QA phase one alpha` / `QA phase one bravo`):
  `pc see | grep -c alpha` → **0**; the whole `ui:` section shows `text "" (466,286 500x314)`.
  Same for the calculator display: `pc see` shows `text "" (378,439 630x46)` whatever is on it.
- The content is right there in AT-SPI — QA read it directly:
  ```
  Atspi.Text.get_text(node, 0, -1)  ->  'QA phase one alpha\nQA phase one bravo'   (editor)
  Atspi.Text.get_text(node, 0, -1)  ->  '7'                                        (calculator)
  ```
- **D4 confirmed still failing, mirrored:** with those same two lines, `pc find "QA phase one alpha"`
  → `551 309`, `pc find "alpha"` → `605 309`, but `pc find "bravo"` → **exit 1**. OCR still drops a
  whole line; only which line changed. So an agent following the skill has *no* working way to read
  document text: OCR misses lines and `ui:` shows nothing.
- Impact: T28a's goal ("an agent learns what is on the screen with one text command") is unmet for
  the case the docs explicitly advertise, and the QA-D4 remedy in `SKILL.md` and
  `README-pc-control.md` is a promise the code does not keep.
- Fix: in `a11y_tree.py`, for nodes exposing `Atspi.Text`, print the first N chars of
  `get_text(0, -1)` (one line, escaped) instead of the empty accessible name — e.g.
  `text "QA phase one alpha ⏎ QA phase one bravo" (466,286 500x314)`, budgeted against `--max-bytes`.
  Until then, remove the D4 claim from both documents.

**D13 — MEDIUM — T28a — an open GTK4 popup menu makes `pc see` report `ui: no accessible tree
(Xwayland or Chrome without ACCESSIBILITY_ENABLED) — use pc shot`, which is both a wrong diagnosis
and the opposite of the ticket's intent; menu contents are never visible in `pc see`.**
- Repro: `pc open gnome-text-editor`; `pc click $(pc tree gnome-text-editor --find "Main Menu")`;
  `pc see` →
  ```
  focus: 1570913258 None "None" 219x522+720+240
  ui: no accessible tree (Xwayland or Chrome without ACCESSIBILITY_ENABLED) - use pc shot
  ```
  A second symptom on the same mechanism: clicking the calculator's `Basic` popover made `pc see`
  print the same message while `focus:` still said `Calculator` (transient; the next call recovered),
  so the message can also appear for an app that *does* have a tree.
- Two causes: (a) `pc see`'s `focus:`/`windows:` lines do **not** apply the transient-row filter that
  T28c gave `pc win list`, so the focused "window" becomes a title-less popup with no AT-SPI app;
  (b) GTK4 popover `menu item` nodes have empty accessible names in this GNOME
  (`menu item "" (738,395 205x32)` × 10), so `--interactive` drops them and even `pc tree` cannot
  name them. (b) is a toolkit limitation; (a) is ours.
- Impact: opening a menu is one of the commonest GUI steps, and the digest answers it with a wrong
  reason and a push to screenshots — exactly the behaviour T28a exists to remove. The wrong message
  will also send agents chasing an `ACCESSIBILITY_ENABLED` problem that does not exist.
- Fix: in `pc see`, resolve `focus:` past transient surfaces to the owning application window
  (reuse the `pc win list` filter), and reserve the "no accessible tree" wording for the case where
  an application really exposes nothing; for a popup, fall back to the parent app's tree and say
  `popup: <WxH+X+Y> (GTK4 menu items are unnamed — use pc find/pc shot)`.

**D14 — LOW — T28a — `pc see --json` ignores `--max-bytes` and is ~3x the text digest, because it
embeds window-calls' raw window dictionaries.**
- Repro: `pc see | wc -c` → 3971; `pc see --json | wc -c` → **11547**;
  `pc see --json --max-bytes 800 | wc -c` → **11547** (unchanged).
  Each `windows` entry carries `area`, `area_all`, `area_cust`, `display`, `frame_type`,
  `window_type`, `layer`, `canclose`, `canmaximize`, `moveable`, `resizeable`, `pid`, … .
- Impact: T28a step 2 says `--json` "returns the same as one object" and the whole ticket is built on
  a ≤ 4 KB budget; an agent that reaches for `--json` (the sensible choice for parsing) pays ~3x the
  tokens and gets no truncation. Minor because the text form is the documented default.
- Also LOW/consistency: the text cap is soft — `--max-bytes 800` → 802 bytes, `--max-bytes 200` →
  314 bytes (the fixed sections are a floor). Harmless, but say so in the usage line.
- Fix: project each window to `{id, wm_class, title, x, y, w, h, focus, minimized}` and apply
  `--max-bytes` to the JSON too (truncating `ui` the same way).

**D15 — MEDIUM — T28b — after a `pc shot --diff --changed-only` that actually wrote a crop, the next
`--diff` on the same path always reports a bogus full-screen change.**
- Repro (screen static between the last two commands):
  ```
  pc shot /tmp/g.png                         # baseline
  pc win move Calculator 300 200             # make something change
  pc shot /tmp/g.png --diff --changed-only   # -> /tmp/g.png 1299x736 253KB ; changed bbox=67,32,1299,736
  sleep 1.5
  pc shot /tmp/g.png --diff --quiet          # -> changed bbox=0,0,1366,768   <-- WRONG, nothing moved
  pc shot /tmp/g.png --diff --quiet          # -> unchanged                    (recovers)
  ```
  Cause: each run rolls the existing output file to `<out>.prev.png` before capturing, so after a
  crop run `prev` is the 1299x736 crop and the 1366x768 comparison degenerates to "everything
  changed". It does not happen when `--changed-only` found nothing to crop (the full frame is kept).
- Impact: `--changed-only` is advertised for the poll loop ("did anything change, and where"), and
  the first poll after every real change is a false positive — the agent is told to look again for
  no reason, which is precisely the cost T28b set out to remove.
- Fix: keep the full frame as the rolling baseline regardless of `--changed-only` (write the crop to
  a separate path, e.g. `<out>.crop.png`, or write `prev` from the captured full image before
  cropping) — and print the crop's path so the agent Reads the right file.

**D16 — LOW — T28b/T28c — dead configuration is still shipped: `~/.config/environment.d/

**D18 — INFO — T28b — `agents-log --pc` counts at most one pixel and one text look per log row, not
per occurrence.**
- The audit log stores one row per Bash call with the full command line in `summary`; a single call
  like `pc shot a.png; pc shot b.png; pc shot c.png` counts as **one** pixel look. Verified against
  the sonnet session: 4 rows → 0 pixel / 3 text, which matched the tool exactly, but only because
  each row held one relevant command.
- Not wrong for the metric's purpose (it measures "looks per turn"), but the README should say so,
  because an agent that batches commands looks cheaper than it is. Note also that the T28b ticket
  text names the log field `command` while T16 actually writes `summary` — `agents-log` uses the
  right one; only the ticket is stale.

## Not testable / out of scope

1. **Persistence across a real login/reboot.** Agent mode surviving a fresh session is proven only
   from configuration (`/etc/dconf/db/local.d/10-agent-mode` present, no user overrides) and human
   mode only from `get_user_value()` being set. Nothing was verified across an actual logout —
   forbidden by the brief and still pending from phase 0.
2. **`boot-check.sh`'s overview close and mode line** were read in the source (lines 23–24), not
   executed, to avoid touching stacks and timers mid-QA.
3. **Chrome's own keyring behaviour under load** — the cold start showed no dialog, but nothing was
   saved to Chrome's password store, so `Chrome Safe Storage` writing into the plaintext keyring is
   unproven by QA. The owner has approved the trade-off (quirks.md, 2026-09-05).
4. **Multi-monitor / lid-open geometry** — everything ran on the single HDMI-1 logical monitor.
   `DisplayConfig` was read-only and never called by any `pc` script.
5. **Concurrency between agents** — QA was the only agent on the desktop. Two agents sharing the
   pointer, focus and clipboard is still untested and unlocked; the phase-1 report already flagged
   this as worth a ticket before Phase 3 puts several agents on timers, and T28's `pc see`/`pc
   wait-for` polling does not change that.
6. **`pc mode` under a live owner session** (owner actually sitting at the machine and fighting the
   agent for focus) — not reproducible by QA.
